# 调研宝后端架构设计方案

> 文档类型：服务端架构设计
>
> 文档版本：v1.0
>
> 文档状态：评审中
>
> 编写日期：2026-08-11
>
> 适用范围：调研宝首期后端服务

---

## 1. 文档目标

本文档定义调研宝后端首期的技术架构、模块边界、数据模型、可靠性策略、部署方式和实施顺序，作为开发、测试、部署和后续扩展的统一依据。

### 1.1 产品范围

- 用户注册、登录和多端会话
- 问卷创建、编辑、发布、下架和版本管理
- 问卷填写、答题提交和提交幂等
- 统计任务、报表生成和任务状态查询
- 调研房间和 WebSocket 实时聊天
- 管理后台、审计日志和运营查询

### 1.2 设计目标

| 目标 | 设计要求 |
| --- | --- |
| 可维护性 | 首期采用模块化单体，业务域清晰分层 |
| 数据可靠性 | PostgreSQL 作为唯一可靠数据源 |
| 性能 | 常规 API P95 目标小于 500 ms；缓存命中接口 P95 目标小于 100 ms |
| 可扩展性 | API 服务、任务 Worker、WebSocket 连接可独立水平扩展 |
| 运维成本 | 优先使用托管 PostgreSQL、Redis 和对象存储 |
| 演进能力 | 通过领域边界、Outbox 事件和独立 Worker 预留拆分能力 |

### 1.3 非目标

- 首期不拆分微服务
- 首期不引入 Kafka、RabbitMQ、Elasticsearch 等重型基础设施
- 不把 Redis 作为业务主库或唯一消息持久化层
- 不以“全链路异步”作为目标；只对 I/O 密集型链路采用异步，对 CPU 密集型任务使用独立 Worker

---

## 2. 架构决策摘要

| 决策项 | 首期方案 | 说明 |
| --- | --- | --- |
| 应用形态 | 模块化单体 | 适合小团队和快速迭代 |
| Web 框架 | FastAPI | 类型校验、OpenAPI、依赖注入和 WebSocket 支持 |
| 主数据库 | PostgreSQL | 事务、约束、聚合分析和 JSONB |
| 缓存 | Redis Cache | 缓存、限流、短期状态和会话辅助 |
| 实时广播 | Redis Pub/Sub | 仅做在线连接广播，不承担可靠投递 |
| 异步任务 | Celery Worker | 统计、报表、通知和定时任务 |
| 可靠事件 | PostgreSQL Outbox | 保证数据库提交与事件发布最终一致 |
| 部署 | 容器 + 云负载均衡 | 每个容器运行一个 Uvicorn 进程，服务通过副本扩容 |
| 文件存储 | 腾讯云 COS | 报表、导出文件和用户上传文件 |

## 3. 总体架构

```text
客户端（App / Web）
        |
        v
腾讯云 CLB / Nginx
        |
        +-----------------------------+
        |                             |
        v                             v
FastAPI API 副本                 WebSocket 连接
        |                             |
        +-------------+---------------+
                      |
       +--------------+------------------+
       |              |                  |
       v              v                  v
PostgreSQL       Redis Cache        Redis Pub/Sub
主数据源        缓存/限流/状态       实时广播
       |
       v
Outbox 事件表
       |
       v
Celery Worker 集群
统计 / 报表 / 通知 / 定时任务
       |
       v
腾讯云 COS
报表与导出文件
```

### 3.1 请求处理链路

1. 客户端请求进入 CLB 或 Nginx。
2. API 服务完成认证、参数校验、权限校验和业务编排。
3. 业务数据写入 PostgreSQL；需要异步处理的事件同时写入 Outbox。
4. 独立发布器或 Worker 投递 Outbox 事件。
5. Celery Worker 执行统计、报表和通知任务。
6. Redis 只负责缓存、短期状态、限流和在线广播。

### 3.2 可靠性原则

- PostgreSQL 是业务事实来源，Redis 丢失后可以重建。
- 重要写操作必须有事务、唯一约束和幂等键。
- WebSocket 广播失败不能回滚已提交的业务数据。
- 异步任务必须可重试、可查询、可人工重跑。
- 所有外部调用必须设置超时，并记录请求 ID。

## 4. 技术选型

### 4.1 核心依赖基线

版本以 2026-08-11 为基线，实际构建使用 lockfile 固定完整依赖树。

| 组件 | 推荐版本/范围 | 备注 |
| --- | --- | --- |
| Python | 3.12 | 生态成熟，作为首期运行时 |
| FastAPI | 0.141.1 | 当前官方发布记录中的稳定版本 |
| Pydantic | 2.13.x | 不假设存在 Pydantic V3 |
| Uvicorn | 0.51.x | 容器内 ASGI Server |
| SQLAlchemy | 2.0.x Async | 异步数据库访问 |
| asyncpg | lockfile 固定 | PostgreSQL 异步驱动 |
| PostgreSQL | 16+ | 使用托管版并启用备份 |
| Redis | 7+ | Cache 和 Broker 建议分离实例 |
| Celery | 5.6.x | 统计、报表和通知任务 |
| Alembic | 最新稳定兼容版本 | 数据库迁移 |
| HTTP 客户端 | httpx | 异步外部 HTTP 调用 |
| 测试 | pytest + pytest-asyncio + httpx | API、异步和集成测试 |
| 质量检查 | Ruff + mypy | Lint、格式化和类型检查 |
| 监控 | Prometheus + Grafana + Sentry | 指标、看板和异常追踪 |

FastAPI 官方发布记录当前列出 `0.141.1`；Pydantic 仍以 2.x 稳定线为主。版本升级必须通过 CI 回归测试后再合入。

### 4.2 依赖管理策略

- 使用 `uv` 管理依赖和生成 `uv.lock`。
- 生产构建只安装 lockfile 中的版本。
- 直接依赖写明兼容范围，间接依赖由 lockfile 固定。
- 每月执行一次依赖升级评估，不自动升级生产环境。
- 版本升级必须通过单元测试、集成测试和基本压测。

│   ├── auth.py
│   ├── users.py
│   ├── surveys.py
│   ├── responses.py
│   ├── tasks.py
│   ├── chat.py
│   └── admin.py
├── models/                    # SQLAlchemy 模型
├── schemas/                   # Pydantic 请求/响应模型
├── repositories/              # 数据访问和查询封装
├── services/                  # 业务规则和事务编排
├── tasks/                     # Celery 任务
├── events/                    # Outbox 事件和发布器

依赖方向固定为：`api -> services -> repositories -> infra`。API 层不直接拼接复杂 SQL，不直接操作 Redis 业务细节。

## 6. 数据架构

### 6.1 核心数据表

| 表 | 用途 | 关键约束 |
| --- | --- | --- |
| users | 用户账号 | 手机号/邮箱唯一 |
| user_sessions | 刷新令牌和会话 | token hash 唯一、支持撤销 |
| surveys | 问卷主实体 | owner_id、状态、当前版本 |
| survey_versions | 问卷不可变版本 | survey_id + version 唯一 |
| questions | 题目定义 | version_id、排序、类型 |
| question_options | 选项定义 | question_id、排序、值唯一 |
| responses | 一次答卷 | survey_version_id、提交幂等键 |
| response_answers | 单题答案 | response_id + question_id 唯一 |
| chat_rooms | 调研房间 | survey_id、访问权限 |
| chat_messages | 聊天消息 | room_id、sender_id、created_at |
| async_tasks | 异步任务 | task_id、状态、错误信息 |
| outbox_events | 可靠事件 | aggregate_id、event_type、published_at |
| audit_logs | 操作审计 | actor_id、action、resource_id |

### 6.2 问卷版本策略

- 编辑中的问卷可以修改草稿版本。
- 发布时生成不可变 `survey_version`。
- 答卷始终关联发布时的版本，不受后续编辑影响。
- 删除采用软删除，重要数据保留审计记录。

### 6.3 JSONB 使用边界

适合 JSONB：题目扩展配置、跳题逻辑、展示配置。

不适合 JSONB：用户、状态、权限、答卷主记录、需要高频筛选和唯一约束的字段。

对于 `structure->>'question_type'` 这类标量查询使用表达式 B-tree 索引；对于 JSONB 包含查询再考虑 GIN 索引。

### 6.4 连接池

连接数按所有进程总量计算：

```text
总连接数 ≈ API 副本数 × 每副本连接数 + Worker 连接数 + 管理连接
```

禁止只按单个 Worker 的 `pool_size` 估算 PostgreSQL 连接。连接池参数必须结合托管数据库的 `max_connections` 和压测结果确定。

## 7. Redis 和异步任务设计

### 7.1 Redis 分层

生产环境至少区分：

| 实例 | 用途 | 数据丢失影响 |
| --- | --- | --- |
| redis-cache | 问卷缓存、限流、短期任务状态 | 可重建 |
| redis-broker | Celery Broker | 任务可能延迟或失败，需重试 |

Redis Pub/Sub 不承担持久化。聊天历史以 PostgreSQL 为准，Redis List 只作为最近消息的读取缓存。

### 7.2 缓存策略

| 数据 | Key 示例 | TTL | 失效方式 |
| --- | --- | --- | --- |
| 已发布问卷 | `survey:published:{id}:{version}` | 10 分钟 | 发布/下架主动删除 |
| 任务状态 | `task:status:{task_id}` | 24 小时 | 任务完成后保留一段时间 |
| 限流计数 | `rate:{scope}:{id}` | 由算法决定 | 自动过期 |
| 最近聊天 | `chat:recent:{room_id}` | 1 小时 | 长度裁剪 + TTL |

缓存未命中时必须区分：数据不存在、缓存过期、Redis 不可用。不能统一返回 `pending`。

### 7.3 Outbox 事件

业务事务内同时写入业务表和 `outbox_events`：

```text
业务数据提交
    ↓ 同一事务
Outbox 事件提交
    ↓
发布器扫描未发布事件
    ↓
Celery / Redis Pub/Sub
    ↓
标记 published_at
```

发布器和消费者都必须支持幂等，事件至少包含 `event_id`、`event_type`、`aggregate_id`、`occurred_at` 和 `payload`。

### 7.4 Celery 任务

- 统计计算：答题提交后异步触发。
- 报表生成：异步生成并上传 COS。
- 通知推送：按渠道独立重试。
- 定时任务：Celery Beat 触发，任务本身保证幂等。
- 失败任务：记录错误、重试次数和最后失败时间，超过阈值进入人工处理队列。

## 8. API 设计规范

### 8.1 路由约定

```text
/api/v1/auth/*
/api/v1/users/*
/api/v1/surveys/*
/api/v1/responses/*
/api/v1/tasks/*
/api/v1/chat/*
/api/v1/admin/*
```

### 8.2 响应约定

成功响应统一包含业务数据；错误响应统一包含：

```json
{
  "code": "SURVEY_NOT_FOUND",
  "message": "survey not found",
  "request_id": "req_01...",
  "details": {}
}
```

### 8.3 写接口要求

- 答卷提交支持 `Idempotency-Key`。
- 创建、发布、下架等状态变更使用数据库事务。
- 所有分页接口使用 cursor 或明确的稳定排序。
- 不向客户端暴露内部异常堆栈和数据库错误。
- 任务查询返回 `pending`、`running`、`success`、`failed`、`expired` 等明确状态。

### 8.4 WebSocket 约定

- 连接建立时完成身份认证和房间权限校验。
- 客户端消息必须经过 Pydantic 校验和长度限制。
- 服务端维护 `message_id`，客户端按 `message_id` 去重。
- 断线重连后从 PostgreSQL 或历史缓存补齐消息。
- Pub/Sub 只负责把消息推送给当前在线连接。
- 对单用户、单房间和单连接分别限流，并处理发送队列背压。

## 9. 安全设计

### 9.1 认证

- Access Token：建议有效期 15 分钟。
- Refresh Token：建议有效期 30 天，服务端只保存 hash。
- Refresh Token 轮换，检测重复使用并撤销会话链。
- 密码使用 Argon2id 或同等级密码哈希算法。
- JWT 密钥和数据库密码使用云 Secret Manager 管理。

### 9.2 授权

- 用户只能访问自己拥有或被授权的问卷。
- 管理员权限采用明确的 RBAC，而不是在路由中散落判断。
- WebSocket 连接必须校验用户、问卷和房间三层关系。

### 9.3 网络安全

- TLS 在 CLB/Nginx 终止，服务间连接按环境要求启用 TLS。
- 正确配置可信代理和真实客户端 IP，不能盲目信任 `X-Forwarded-For`。
- 明确配置 CORS 来源，不使用通配符放开生产 API。
- 上传文件使用白名单扩展名、大小限制、病毒扫描和私有 COS URL。

## 10. 部署和容量设计

### 10.1 容器部署

- 一个 API 容器运行一个 Uvicorn 进程。
- 通过 CLB/TKE 扩展 API 副本。
- Celery Worker 使用独立 Deployment 或云主机组。
- WebSocket 连接和普通 API 可使用同一应用，但资源限额和监控指标分开。
- 发布采用滚动更新，先启动新副本，再逐步摘除旧副本。

### 10.2 健康检查

| 接口 | 用途 | 检查内容 |
| --- | --- | --- |
| `/health/live` | 存活探针 | 进程是否可响应 |
| `/health/ready` | 就绪探针 | PostgreSQL、Redis 是否可用 |
| `/metrics` | 指标采集 | API、任务和连接指标 |

### 10.3 容量估算原则

初始容量不直接套用固定连接池和 Worker 数量，按以下顺序确定：

1. 设定并发用户、请求 QPS、WebSocket 连接数和任务吞吐目标。
2. 使用代表性数据量进行压测。
3. 观察 API P95/P99、数据库连接、锁等待、Redis 命中率和任务积压。
4. 根据瓶颈调整副本、连接池、缓存和 Worker 并发。

## 11. 可观测性和运维

### 11.1 日志

结构化 JSON 输出到标准输出，至少包含：

- `timestamp`
- `level`
- `request_id`
- `trace_id`
- `user_id`
- `route`
- `status_code`
- `duration_ms`
- `error_code`

### 11.2 指标

- API QPS、P50/P95/P99、错误率
- PostgreSQL 连接数、慢查询、锁等待、事务耗时
- Redis 命中率、内存、连接数、驱逐数量
- Celery 队列长度、任务耗时、重试数和失败数
- WebSocket 当前连接数、断开数、广播延迟和发送队列积压

### 11.3 数据保护

- PostgreSQL 开启自动备份和 PITR。
- 明确 RPO、RTO 和数据保留周期。
- 每月至少执行一次恢复演练。
- Alembic 迁移在发布流程中执行，禁止手工修改生产表结构。

## 14. 评审前需要确认的问题

| 问题 | 影响 |
| --- | --- |
| 首期注册用户和峰值并发是多少 | API 副本、数据库和 Redis 规格 |
| 单个问卷最大题目数和答卷量是多少 | JSONB、索引和分区策略 |
| 聊天消息需要保存多久 | PostgreSQL 存储和归档策略 |
| 报表是否需要异步导出大文件 | Celery、COS 和下载权限 |
| 是否有短信、邮件、App Push | 外部服务适配和重试策略 |
| 目标 RPO/RTO 是多少 | 备份、容灾和托管服务等级 |
| 是否需要多租户 | tenant_id、隔离和权限模型 |
