# 调研宝后端架构设计方案

> 文档类型：服务端架构设计
> 文档版本：v2.1
> 文档状态：评审中
> 编写日期：2026-08-12
> 适用范围：调研宝首期后端服务
> 基于：v1.0 方案 + 技术选型融合优化

---

## 1. 文档目标

本文档定义调研宝后端首期的技术架构、模块边界、数据模型、统一响应规范、Token 认证机制、项目文件划分、可靠性策略、部署方式和实施顺序，作为开发、测试、部署和后续扩展的统一依据。

### 1.1 产品范围

- 用户注册、登录和多端会话
- 问卷创建、编辑、发布、下架和版本管理
- 问卷填写、答题提交和提交幂等
- 统计任务、报表生成和任务状态查询
- 调研房间和 WebSocket 实时聊天
- 管理后台、审计日志和运营查询

### 1.2 设计目标

| 目标 | 设计要求 |
| --- | --- |
| 可维护性 | 首期采用模块化单体，业务域清晰分层 |
| 数据可靠性 | PostgreSQL 作为唯一可靠数据源 |
| 性能 | 常规 API P95 < 500ms；缓存命中接口 P95 < 100ms |
| 可扩展性 | API 服务、任务 Worker、WebSocket 连接可独立水平扩展 |
| 运维成本 | 优先使用托管 PostgreSQL、Redis 和对象存储 |
| 演进能力 | 通过领域边界、Outbox 事件和独立 Worker 预留拆分能力 |

### 1.3 非目标

- 首期不拆分微服务
- 首期不引入 Kafka、RabbitMQ、Elasticsearch 等重型基础设施
- 不把 Redis 作为业务主库或唯一消息持久化层
- 不以"全链路异步"作为目标；只对 I/O 密集型链路采用异步，CPU 密集型任务使用独立 Worker

## 2. 架构决策摘要

| 决策项 | 首期方案 | 说明 |
| --- | --- | --- |
| 应用形态 | 模块化单体 | 适合小团队和快速迭代 |
| Web 框架 | FastAPI 0.141.x | 类型校验、OpenAPI、依赖注入和 WebSocket 原生支持 |
| 主数据库 | PostgreSQL 16+ | 事务、JSONB、聚合分析，托管版 + PITR |
| ORM | SQLAlchemy 2.0 Async | 异步数据库访问 + Alembic 迁移 |
| 缓存 | Redis Cache（独立实例） | 缓存、限流、在线状态、最近消息 |
| 消息代理 | Redis Broker（独立实例） | Celery Broker，与 Cache 物理分离 |
| 实时广播 | Redis Pub/Sub | 跨副本在线连接广播，不承担可靠投递 |
| 异步任务 | Celery 5.6 + Beat | 统计、报表、通知、定时任务 |
| 可靠事件 | PostgreSQL Outbox | 业务提交与事件发布最终一致 |
| 文件存储 | 腾讯云 COS | 报表、导出文件和用户上传 |
| 认证 | JWT + Refresh Token 轮换 | Access 15min / Refresh 30天 |
| 密码哈希 | Argon2id | 抗 GPU 暴力破解 |
| 部署 | 腾讯云 CLB + TKE + Docker | 每容器 1 Uvicorn 进程，滚动更新 |
| 可观测性 | Prometheus + Grafana + Sentry | 指标、看板、异常追踪 |

## 3. 总体架构

```text
客户端（App / Web / 小程序）
        │
        ▼ HTTPS / WSS
腾讯云 CLB（TLS 终止 + 负载均衡 + WS 升级）
        │
        ├─────────────────────────────┐
        ▼                             ▼
FastAPI API 副本（多副本）         WebSocket 连接
        │                             │
        └─────────────┬───────────────┘
                      │
       ┌──────────────┼──────────────────┐
       ▼              ▼                  ▼
PostgreSQL 16    Redis Cache        Redis Broker
主数据源         缓存/限流/状态       Celery 队列
       │              │                  │
       ▼              │                  ▼
Outbox 事件表         │          Celery Worker 集群
       │              │          统计/报表/通知/定时
       ▼              │                  │
事件发布器 ◄──────────┘                  ▼
                              腾讯云 COS（报表/导出）
```

### 3.1 请求处理链路

1. 客户端请求进入 CLB，TLS 终止后转发到 FastAPI 副本
2. API 服务完成认证、参数校验、权限校验和业务编排
3. 业务数据写入 PostgreSQL；需要异步处理的事件同时写入 Outbox（同一事务）
4. 独立发布器扫描 Outbox 并投递事件到 Celery / Redis Pub/Sub
5. Celery Worker 执行统计、报表和通知任务，结果写入 PG 或上传 COS
6. Redis Cache 负责缓存、短期状态、限流和在线广播，丢失可重建

### 3.2 可靠性原则

- PostgreSQL 是业务事实来源，Redis 丢失后可以重建
- 重要写操作必须有事务、唯一约束和幂等键
- WebSocket 广播失败不能回滚已提交的业务数据
- 异步任务必须可重试、可查询、可人工重跑
- 所有外部调用必须设置超时，并记录 request_id

## 4. 技术选型详细清单

### 4.1 核心依赖基线

| 组件 | 推荐版本 | 备注 |
| --- | --- | --- |
| Python | 3.12 | 生态成熟，async 性能好 |

| Pydantic | 2.13.x | 不假设 Pydantic V3 |
| Uvicorn | 0.51.x | 容器内 ASGI Server |
| SQLAlchemy | 2.0.x Async | 异步 ORM |
| asyncpg | lockfile 固定 | PostgreSQL 异步驱动 |

| Celery | 5.6.x | 异步任务 + Beat 定时 |
| Alembic | 最新稳定 | 数据库迁移 |
| httpx | 最新稳定 | 异步外部 HTTP 客户端 |
| python-jose | 最新稳定 | JWT 编解码 |
| passlib[argon2] | 最新稳定 | Argon2id 密码哈希 |
| python-multipart | 最新稳定 | 文件上传支持 |
| pytest | 最新稳定 | 测试框架 |
| pytest-asyncio | 最新稳定 | 异步测试 |
| Ruff | 最新稳定 | Lint + 格式化 |
| mypy | 最新稳定 | 类型检查 |
| uv | 最新稳定 | 依赖管理 |
| prometheus-client | 最新稳定 | 指标采集 |
| sentry-sdk | 最新稳定 | 异常追踪 |

### 4.2 依赖管理策略

- 使用 `uv` 管理依赖和生成 `uv.lock`
- 生产构建只安装 lockfile 中的版本
- 直接依赖写明兼容范围，间接依赖由 lockfile 固定
- 每月执行一次依赖升级评估，不自动升级生产环境
- 版本升级必须通过单元测试、集成测试和基本压测

### 5.2 各文件职责详细说明

#### 5.2.2 Core 核心层（`app/core/`）

| 文件 | 职责 | 关键内容 |
| --- | --- | --- |
| `config.py` | 环境配置管理 | 使用 pydantic-settings 定义 Settings 类，读取环境变量；包含数据库 URL、Redis URL、JWT 密钥、COS 配置、环境标识等 |

## 6. 统一前端响应格式

### 6.1 设计原则

- 所有 HTTP 接口（成功/失败）返回统一的 JSON 结构
- 前端通过 `code` 判断业务结果，通过 `data` 获取业务数据
- 分页接口使用统一的分页结构
- 错误响应包含足够的调试信息，但不暴露内部堆栈

### 6.2 成功响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "request_id": "req_01HXYZ1234567890",
  "timestamp": 1781234567890
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `code` | int | 是 | 业务状态码，`0` 表示成功，非 0 表示业务错误 |
| `message` | string | 是 | 状态描述，成功时为 `"success"` |
| `data` | object/array/null | 是 | 业务数据，无数据时为 `null` |
| `request_id` | string | 是 | 请求唯一标识，用于链路追踪 |
| `timestamp` | long | 是 | 服务端响应时间戳（毫秒） |

### 6.3 分页响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [ ],
    "pagination": {
      "page": 1,
      "page_size": 20,
      "total": 156,
      "total_pages": 8,
      "has_next": true,
      "has_prev": false,
      "next_cursor": "eyJpZCI6MTB9"
    }
  },
  "request_id": "req_01HXYZ1234567890",
  "timestamp": 1781234567890
}
```

| 分页字段 | 类型 | 说明 |
| --- | --- | --- |
| `items` | array | 当前页数据列表 |
| `pagination.page` | int | 当前页码（从 1 开始） |
| `pagination.page_size` | int | 每页条数 |
| `pagination.total` | long | 总记录数 |
| `pagination.total_pages` | int | 总页数 |
| `pagination.has_next` | bool | 是否有下一页 |
| `pagination.has_prev` | bool | 是否有上一页 |
| `pagination.next_cursor` | string/null | 游标分页时的下一页游标，偏移分页时为 null |

### 6.4 错误响应格式

```json
{
  "code": 40001,
  "message": "用户不存在",
  "data": null,
  "request_id": "req_01HXYZ1234567890",
  "timestamp": 1781234567890,
  "details": {
    "field": "user_id",
    "value": "99999"
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `code` | int | 是 | 业务错误码（非 0） |
| `message` | string | 是 | 面向用户的错误描述 |
| `data` | null | 是 | 错误响应固定为 null |
| `request_id` | string | 是 | 请求唯一标识 |
| `timestamp` | long | 是 | 响应时间戳 |
| `details` | object | 否 | 错误详情（字段级错误、参数校验错误等），生产环境敏感信息需脱敏 |

### 6.5 错误码规范

错误码采用 5 位数字，前 2 位为业务域，后 3 位为具体错误：

| 错误码范围 | 业务域 | 示例 |
| --- | --- | --- |
| `0` | 成功 | `0` - 成功 |
| `10000-10999` | 系统通用 | `10001` - 参数校验失败、`10002` - 请求过于频繁 |
| `11000-11999` | 认证授权 | `11001` - 未登录、`11002` - Token 过期、`11003` - 权限不足 |
| `12000-12999` | 用户模块 | `12001` - 用户不存在、`12002` - 手机号已注册、`12003` - 密码错误 |
| `13000-13999` | 问卷模块 | `13001` - 问卷不存在、`13002` - 问卷已发布不可编辑、`13003` - 问卷已下架 |
| `14000-14999` | 答卷模块 | `14001` - 答卷不存在、`14002` - 重复提交、`14003` - 问卷未发布 |
| `15000-15999` | 任务模块 | `15001` - 任务不存在、`15002` - 任务执行失败、`15003` - 任务已取消 |
| `16000-16999` | 聊天模块 | `16001` - 房间不存在、`16002` - 非房间成员、`16003` - 消息发送失败 |
| `17000-17999` | 文件存储 | `17001` - 文件上传失败、`17002` - 文件过大、`17003` - 文件格式不支持 |
| `50000-50999` | 服务端错误 | `50000` - 内部服务器错误、`50001` - 数据库异常、`50002` - 缓存不可用 |

### 6.6 HTTP 状态码与业务错误码关系

| HTTP 状态码 | 场景 | 业务 code 范围 |
| --- | --- | --- |
| `200` | 业务成功 | `0` |
| `400` | 参数校验失败 | `10001` |
| `401` | 未认证 / Token 失效 | `11001` / `11002` |
| `403` | 权限不足 | `11003` |
| `404` | 资源不存在 | 各模块 `xx001` |
| `409` | 资源冲突（重复提交） | `14002` |
| `429` | 请求限流 | `10002` |
| `500` | 服务端内部错误 | `50000+` |

### 6.7 统一响应封装实现（`app/core/response.py`）

```python
from typing import Generic, TypeVar, Optional, Any
from pydantic import BaseModel
from datetime import datetime

T = TypeVar("T")

class ApiResponse(BaseModel, Generic[T]):
    code: int
    message: str
    data: Optional[T]
    request_id: str
    timestamp: int

class Pagination(BaseModel):
    page: int
    page_size: int
    total: int
    total_pages: int
    has_next: bool
    has_prev: bool
    next_cursor: Optional[str] = None

class PageResult(BaseModel, Generic[T]):
    items: list[T]
    pagination: Pagination

def success(data: Any = None, message: str = "success") -> dict:
    return {
        "code": 0,
        "message": message,
        "data": data,
        "request_id": get_current_request_id(),
        "timestamp": int(datetime.now().timestamp() * 1000),
    }

def error(code: int, message: str, details: Optional[dict] = None) -> dict:
    resp = {
        "code": code,
        "message": message,
        "data": None,
        "request_id": get_current_request_id(),
        "timestamp": int(datetime.now().timestamp() * 1000),
    }
    if details:
        resp["details"] = details
    return resp

def paginated(items: list, page: int, page_size: int, total: int) -> dict:
    total_pages = (total + page_size - 1) // page_size
    return success({
        "items": items,
        "pagination": {
            "page": page,
            "page_size": page_size,
            "total": total,
            "total_pages": total_pages,
            "has_next": page < total_pages,
            "has_prev": page > 1,
            "next_cursor": None,
        }
    })
```

## 7. Token 验证机制

### 7.1 认证方案概述

采用 **JWT Access Token + Refresh Token 轮换** 双 Token 机制：

| Token 类型 | 有效期 | 存储位置 | 用途 |
| --- | --- | --- | --- |
| Access Token | 15 分钟 | 前端内存 / localStorage | 接口访问鉴权 |
| Refresh Token | 30 天 | 服务端数据库（仅存 hash）+ 前端安全存储 | 刷新 Access Token |

### 7.2 JWT Token 结构

#### Access Token Payload

```json
{
  "sub": "user_12345",
  "type": "access",
  "iat": 1781234567,
  "exp": 1781235467,
  "jti": "tok_01HXYZ123",
  "user_id": 12345,
  "role": "user",
  "session_id": "sess_01HABC456"
}
```

| 字段 | 说明 |
| --- | --- |
| `sub` | 主题，用户唯一标识 |
| `type` | Token 类型，固定 `"access"` |
| `iat` | 签发时间（Unix 时间戳） |
| `exp` | 过期时间（Unix 时间戳） |
| `jti` | Token 唯一 ID，用于黑名单 |
| `user_id` | 用户数据库 ID |
| `role` | 用户角色（`user` / `admin`） |
| `session_id` | 关联的会话 ID，用于登出撤销 |

#### Refresh Token Payload

```json
{
  "sub": "user_12345",
  "type": "refresh",
  "iat": 1781234567,
  "exp": 1783826567,
  "jti": "ref_01HXYZ789",
  "user_id": 12345,
  "session_id": "sess_01HABC456",
  "device_info": "ios/17.0/iPhone15"
}
```

### 7.3 Token 验证流程

```
客户端请求（Header: Authorization: Bearer <access_token>）
    │
    ▼
FastAPI 依赖 get_current_user
    │
    ├─ 1. 提取 Token（从 Authorization Header）
    │
    ├─ 2. 验证 JWT 签名（HS256 / RS256）
    │     ├─ 签名无效 → 401 错误码 11001
    │     └─ 签名有效 → 继续
    │
    ├─ 3. 验证 Token 类型（必须为 access）
    │     └─ 类型错误 → 401 错误码 11001
    │
    ├─ 4. 验证过期时间 exp
    │     └─ 已过期 → 401 错误码 11002（Token 已过期）
    │
    ├─ 5. 检查会话是否有效（查 user_sessions 表 / Redis 缓存）
    │     ├─ 会话已撤销（登出/密码修改）→ 401 错误码 11001
    │     └─ 会话有效 → 继续
    │
    ├─ 6. 查询用户信息（优先 Redis 缓存，未命中查 DB）
    │     ├─ 用户不存在/已禁用 → 401 错误码 12001
    │     └─ 用户正常 → 返回 User 对象
    │
    ▼
注入到路由函数的 current_user 参数
```

### 7.4 Token 刷新流程

```
前端检测到 Access Token 即将过期（剩余 < 2 分钟）
    │
    ▼
POST /api/v1/auth/refresh
Body: { "refresh_token": "<refresh_token>" }
    │
    ▼
服务端验证 Refresh Token
    ├─ 签名验证
    ├─ 类型验证（必须为 refresh）
    ├─ 过期验证
    ├─ 查 user_sessions 表验证 token hash 匹配
    └─ 检测是否被重复使用（Refresh Token 轮换检测）
    │
    ├─ 验证失败 → 401，要求重新登录
    │
    └─ 验证成功 → 签发新的 Access Token + 新的 Refresh Token
         ├─ 旧 Refresh Token 标记为已使用
         ├─ 创建新会话记录
         └─ 返回新的双 Token
```

### 7.5 Refresh Token 轮换与安全检测

- 每次刷新都会签发**新的 Refresh Token**，旧的立即失效
- 服务端记录每个 Refresh Token 的使用状态
- 如果检测到**已使用过的 Refresh Token** 再次被使用，判定为 Token 泄露：
  - 立即撤销该用户的所有会话
  - 强制所有设备重新登录
  - 记录安全审计日志

### 7.6 登出流程

```
POST /api/v1/auth/logout
Header: Authorization: Bearer <access_token>
    │
    ▼
1. 从 Access Token 解析 session_id
2. 删除 user_sessions 表中对应记录
3. 删除 Redis 中的会话缓存和用户信息缓存
4. 将 Access Token 的 jti 加入 Redis 黑名单（直到自然过期）
5. 返回成功
```

### 7.7 密码修改后的会话处理

- 用户修改密码后，撤销该用户**所有设备**的会话
- 清除 Redis 中该用户的所有缓存
- 所有旧 Token 立即失效

### 7.8 鉴权依赖实现（`app/api/deps.py`）

```python
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from jose import JWTError, jwt
from app.core.config import settings
from app.core.security import verify_token
from app.infra.db import get_db_session
from app.models.user import User
from app.infra.redis_cache import get_redis_cache

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")

async def get_current_user(
    token: str = Depends(oauth2_scheme),
    db = Depends(get_db_session),
    redis = Depends(get_redis_cache),
) -> User:
    # 1. 验证 JWT
    try:
        payload = verify_token(token, token_type="access")
    except JWTError:
        raise HTTPException(status_code=401, detail={"code": 11001, "message": "无效的认证凭证"})

    user_id = payload.get("user_id")
    session_id = payload.get("session_id")
    jti = payload.get("jti")

    # 2. 检查 Token 黑名单
    if await redis.exists(f"token:blacklist:{jti}"):
        raise HTTPException(status_code=401, detail={"code": 11001, "message": "Token 已撤销"})

    # 3. 检查会话有效性
    session_key = f"session:valid:{session_id}"
    session_valid = await redis.get(session_key)
    if session_valid is None:
        # 缓存未命中，查数据库
        session = await db.execute(...)
        if not session:
            raise HTTPException(status_code=401, detail={"code": 11001, "message": "会话已失效"})
        await redis.setex(session_key, 300, "1")  # 缓存 5 分钟
    elif session_valid == b"0":
        raise HTTPException(status_code=401, detail={"code": 11001, "message": "会话已失效"})

    # 4. 获取用户信息（优先缓存）
    user_key = f"user:info:{user_id}"
    user_data = await redis.get(user_key)
    if user_data:
        return User.parse_raw(user_data)

    user = await db.get(User, user_id)
    if not user or user.is_deleted:
        raise HTTPException(status_code=401, detail={"code": 12001, "message": "用户不存在"})
    if user.status != "active":
        raise HTTPException(status_code=401, detail={"code": 12004, "message": "账号已被禁用"})

    await redis.setex(user_key, 600, user.json())
    return user
```

### 7.9 WebSocket 鉴权

WebSocket 连接在握手阶段完成鉴权，有两种方式：

**方式一：Query 参数传递 Token（推荐，浏览器 WS 不支持自定义 Header）**

```
wss://api.example.com/api/v1/ws/chat?token=<access_token>&room_id=123
```

**方式二：连接建立后第一条消息发送 Token**

```json
{ "type": "auth", "token": "<access_token>" }
```

鉴权流程与 HTTP 接口一致，验证通过后绑定用户身份到 Connection，验证失败立即关闭连接（code 4401）。

## 8. 应用分层规范

### 8.1 分层依赖方向

```

```

**依赖规则：**
- API 层不直接操作数据库或 Redis，必须通过 Service 层
- Service 层不直接拼接 SQL，通过 Repository 层访问数据
- Repository 层只做数据读写，不包含业务逻辑
- 各层之间通过依赖注入解耦，便于单元测试

### 8.2 事务管理

- 事务边界在 Service 层，使用 `@Transactional` 装饰器或上下文管理器
- 一个 Service 方法内的多个数据库操作在同一事务中
- Outbox 事件与业务数据在同一事务中写入
- 跨 Service 调用时，事务由最上层 Service 管理

## 9. 数据架构

### 9.1 核心数据表

| 表 | 用途 | 关键约束 |
| --- | --- | --- |
| `users` | 用户账号 | 手机号/邮箱唯一、密码哈希 |
| `user_sessions` | 刷新令牌会话 | token hash 唯一、支持撤销、设备信息 |
| `surveys` | 问卷主实体 | owner_id、状态、当前版本号 |
| `survey_versions` | 问卷不可变版本 | survey_id + version 唯一 |
| `questions` | 题目定义 | version_id、排序、类型、JSONB 扩展配置 |
| `question_options` | 选项定义 | question_id、排序、值唯一 |
| `responses` | 一次答卷 | survey_version_id、提交幂等键唯一 |
| `response_answers` | 单题答案 | response_id + question_id 唯一、JSONB 答案 |
| `chat_rooms` | 调研房间 | survey_id、访问权限 |
| `chat_messages` | 聊天消息 | room_id、sender_id、msg_seq、created_at |
| `async_tasks` | 异步任务 | task_id 唯一、状态、错误信息 |
| `outbox_events` | 可靠事件 | aggregate_id、event_type、published_at |
| `audit_logs` | 操作审计 | actor_id、action、resource_id |

### 9.2 问卷版本策略

- 编辑中的问卷可以修改草稿版本
- 发布时生成不可变 `survey_version` 快照
- 答卷始终关联发布时的版本，不受后续编辑影响
- 删除采用软删除（`is_deleted`），重要数据保留审计记录

### 9.3 JSONB 使用边界

**适合 JSONB：**
- 题目扩展配置（跳题逻辑、展示配置、校验规则）
- 答卷答案内容（不同题型答案结构不同）
- 审计日志的变更前/后数据

**不适合 JSONB：**
- 用户、状态、权限等需要频繁筛选的字段
- 答卷主记录
- 需要唯一约束的字段

**索引策略：**
- 标量查询（如 `structure->>'question_type'`）使用表达式 B-tree 索引
- JSONB 包含查询使用 GIN 索引

### 9.4 连接池规划

总连接数按所有进程总量计算：

```
总连接数 ≈ API 副本数 × 每副本 pool_size + Worker 数 × 每 Worker pool_size + 管理连接
```

- 禁止只按单个进程的 `pool_size` 估算
- 连接池参数必须结合托管 PostgreSQL 的 `max_connections` 和压测结果确定
- 建议初始配置：每 API 副本 `pool_size=10, max_overflow=20`；每 Worker `pool_size=5`

## 10. Redis 和异步任务设计

### 10.1 Redis 实例分层

生产环境至少部署两个独立 Redis 实例：

| 实例 | 用途 | 驱逐策略 | 数据丢失影响 |
| --- | --- | --- | --- |
| `redis-cache` | 问卷缓存、限流、在线状态、最近消息、用户信息缓存 | `allkeys-lru` | 可重建，短暂性能下降 |
| `redis-broker` | Celery Broker、任务状态 | `noeviction` | 任务可能延迟，需重试机制 |

### 10.2 缓存策略

| 数据 | Key 示例 | TTL | 失效方式 |
| --- | --- | --- | --- |
| 已发布问卷 | `survey:published:{id}:{version}` | 10 分钟 | 发布/下架主动删除 |
| 用户信息 | `user:info:{user_id}` | 10 分钟 | 修改资料/登出主动删除 |
| 会话有效性 | `session:valid:{session_id}` | 5 分钟 | 登出/密码修改主动删除 |
| 任务状态 | `task:status:{task_id}` | 24 小时 | 任务完成后保留 |
| 限流计数 | `rate:{scope}:{id}` | 算法决定 | 自动过期 |
| 最近聊天 | `chat:recent:{room_id}` | 1 小时 | LPUSH + LTRIM 裁剪 100 条 |
| 在线用户 | `chat:online:{room_id}` | — | Set，上下线维护 |
| 未读计数 | `chat:unread:{user_id}:{room_id}` | 7 天 | 读消息时 DECR |
| Token 黑名单 | `token:blacklist:{jti}` | Token 剩余有效期 | 自动过期 |

缓存未命中时必须区分：数据不存在、缓存过期、Redis 不可用，不能统一返回 `pending`。

### 10.3 Outbox 事件模式

```
业务数据提交
    ↓ 同一事务
Outbox 事件写入 outbox_events 表
    ↓
Publisher 定时扫描未发布事件（每 1 秒）
    ↓
投递到 Celery 任务队列 / Redis Pub/Sub
    ↓
标记 published_at
    ↓
定期归档已发布事件（保留 30 天后清理）
```

事件必须包含：`event_id`、`event_type`、`aggregate_id`、`occurred_at`、`payload`（JSONB）。
发布器和消费者都必须支持幂等处理。

### 10.4 Celery 任务设计

| 任务类型 | 触发方式 | 重试策略 | 超时 |
| --- | --- | --- | --- |
| 统计计算 | 答卷提交后 Outbox 事件触发 | 最多 3 次，指数退避 | 5 分钟 |
| 报表生成 | 用户手动触发 | 最多 2 次 | 30 分钟 |
| 通知推送 | 事件触发 | 最多 5 次，按渠道差异化 | 1 分钟 |
| 定时任务 | Celery Beat 调度 | 任务自身保证幂等 | 按任务定 |
| Outbox 发布 | 每 1 秒定时 | 无重试（下次扫描会继续） | 30 秒 |

失败任务记录错误信息、重试次数和最后失败时间，超过阈值进入人工处理队列。

## 11. 聊天室模块详细设计

### 11.1 消息发送链路

```
客户端发送 WS 消息
    │
    ▼
WebSocket Connection 接收 → Pydantic 校验 + 长度限制 + 限流
    │
    ▼
PostgreSQL 事务：
  ├─ INSERT chat_messages（room_id, sender_id, content, msg_seq）
  └─ INSERT outbox_events（chat.message_sent）
    │
    ▼
事务提交成功
    │
    ├─ Redis LPUSH chat:recent:{room_id}（LTRIM 保留 100 条）
    ├─ Redis PUBLISH chat:room:{room_id}（广播消息）
    ├─ Redis HINCRBY chat:unread:{user_id}:{room_id}（其他成员未读 +1）
    └─ 给发送方返回 ACK（含 message_id, msg_seq, server_time）
    │
    ▼
各 API 副本 Broadcaster 收到 Pub/Sub 消息
    │
    ▼
Connection Manager 推送给本节点该房间的所有在线连接
```

### 11.2 消息接收与展示

- 客户端收到消息后按 `msg_seq` 排序展示
- 客户端本地维护 `last_received_seq`，用于断线重连补齐
- 消息去重：客户端按 `message_id` 去重

### 11.3 轮询数据性能保障

| 接口 | 数据来源 | 预期延迟 | 说明 |
| --- | --- | --- | --- |
| 未读消息数 | Redis Hash | < 5ms | 完全不查 DB |
| 房间在线列表 | Redis Set | < 5ms | 完全不查 DB |
| 任务状态 | Redis String | < 5ms | 完全不查 DB |
| 最近消息（首屏） | Redis List | < 5ms | 缓存命中时不查 DB |
| 历史消息翻页 | PostgreSQL | < 50ms | 走索引分页查询 |

### 11.4 在线状态与心跳

```
连接建立 → SADD chat:online:{room_id} {user_id}
         → SET chat:heartbeat:{user_id}:{room_id} 1 EX 90

每 30s 客户端发送 ping → 服务端刷新 EXPIRE 为 90s

心跳超时（90s 无 ping）→ 视为离线
  → SREM chat:online:{room_id} {user_id}
  → PUBLISH 房间用户离线事件
  → 关闭 WebSocket 连接
```

### 11.5 断线重连与消息补齐

```
客户端重连 → 携带 last_received_seq
    │
    ▼
服务端查询 Redis List（最近 100 条）
  ├─ 增量在缓存范围内 → 直接返回缓存中的增量消息
  └─ 超出缓存范围 → 查 PostgreSQL
       WHERE room_id = ? AND msg_seq > last_received_seq
       ORDER BY msg_seq ASC LIMIT 100
```

### 11.6 限流与背压

- 单连接消息发送限流：10 条/秒
- 单用户跨连接限流：20 条/秒
- 单房间消息限流：100 条/秒
- 发送队列积压超过阈值时，发送 `slow_down` 控制消息给客户端
- 超过最大消息长度（4KB）直接拒绝

## 12. 安全设计

### 12.1 认证安全

- Access Token 有效期 15 分钟，Refresh Token 30 天
- Refresh Token 轮换，检测重复使用并撤销全部会话
- 密码使用 Argon2id 哈希，参数：`time_cost=3, memory_cost=64MB, parallelism=4`
- JWT 密钥和数据库密码使用云 Secret Manager 管理，不写入代码
- 登录失败次数限制：5 次失败后锁定 15 分钟

### 12.2 授权

- 用户只能访问自己拥有或被授权的问卷
- 管理员权限采用 RBAC，在 `api/deps.py` 中统一校验
- WebSocket 连接必须校验用户、问卷和房间三层关系
- 接口级别权限通过依赖注入装饰器实现

### 12.3 网络安全

- TLS 在 CLB 终止，强制 HTTPS/WSS
- 正确配置可信代理和真实客户端 IP，不盲目信任 `X-Forwarded-For`
- 明确配置 CORS 来源白名单，生产环境不使用通配符
- 上传文件使用白名单扩展名、大小限制（最大 50MB）、私有 COS URL
- 所有接口默认开启限流，匿名接口更严格

### 12.4 数据安全

- 敏感字段（手机号、邮箱）数据库存储加密或脱敏展示
- 审计日志记录所有写操作和权限变更
- 数据库开启自动备份和 PITR，RPO < 5 分钟
- 定期执行恢复演练（每月至少一次）

## 13. 部署和容量设计

### 13.1 容器部署

- 一个 API 容器运行一个 Uvicorn 进程（`--workers 1`）
- 通过 TKE Deployment 扩展 API 副本数
- Celery Worker 使用独立 Deployment，可独立扩缩
- WebSocket 连接和普通 API 使用同一应用，但资源限额和监控分开
- 发布采用滚动更新：先启动新副本 → 健康检查通过 → 逐步摘除旧副本

### 13.2 健康检查

| 接口 | 用途 | 检查内容 |
| --- | --- | --- |
| `/health/live` | 存活探针 | 进程是否可响应 HTTP |
| `/health/ready` | 就绪探针 | PostgreSQL、Redis 连接是否可用 |
| `/metrics` | 指标采集 | Prometheus 格式指标 |

### 13.3 容量估算原则

不直接套用固定参数，按以下顺序确定：

1. 设定并发用户、请求 QPS、WebSocket 连接数和任务吞吐目标
2. 使用代表性数据量进行压测
3. 观察 API P95/P99、数据库连接、锁等待、Redis 命中率和任务积压
4. 根据瓶颈调整副本数、连接池、缓存策略和 Worker 并发

**初始参考配置（百人量级）：**
- API 副本：2 个（2C4G 各）
- PostgreSQL：2C4G 托管版
- Redis Cache：1C2G
- Redis Broker：1C2G
- Celery Worker：2 个并发

## 14. 可观测性

### 14.1 日志

结构化 JSON 输出到标准输出，至少包含：

- `timestamp` - 时间戳
- `level` - 日志级别
- `request_id` - 请求 ID
- `trace_id` - 链路追踪 ID
- `user_id` - 用户 ID（如有）
- `route` - 请求路由
- `method` - HTTP 方法
- `status_code` - 响应状态码
- `duration_ms` - 请求耗时
- `error_code` - 业务错误码（如有）
- `error_message` - 错误信息（如有）

### 14.2 指标

| 类别 | 指标 |
| --- | --- |
| API | QPS、P50/P95/P99 延迟、错误率、各端点流量 |
| PostgreSQL | 连接数、慢查询、锁等待、事务耗时、缓存命中率 |
| Redis | 命中率、内存使用、连接数、驱逐数量、延迟 |
| Celery | 队列长度、任务耗时、重试数、失败数、Worker 存活 |
| WebSocket | 当前连接数、断开率、广播延迟、发送队列积压 |
| 业务 | 答卷提交量、问卷发布量、聊天消息量 |

### 14.3 告警

- API P95 > 500ms 持续 5 分钟
- API 错误率 > 5% 持续 3 分钟
- PostgreSQL 连接数 > 80% 上限
- Redis 内存使用 > 80%
- Celery 队列积压 > 1000 条
- WebSocket 连接数异常下降 > 30%
